- 用户提供的译文包有 1,908 条，其中阶段 5 有 1,773 条，占 92.92%。阶段 5 表示译文已校对，并不等于全部都已接入游戏。

## 为什么改这些代码

1. 正文原字库没有足够汉字。新增小、中、大三档字模，缺字从固定版本的开源字体生成；标题描边字体只收录实际用到的汉字，减少 ROM 占用。
2. 小号正文原先把高分辨率字形的像素作 OR 合并，复杂字如“蹑”会糊成白块。现在优先选更合适的 12px 字源并用点采样；“蹑”另有保留左右空列的 9×9 手工字模。关卡名使用另一套 16×16 描边标题字库，因此还要让小号标题复用这份手工骨架，并把八方向描边缩成四方向薄描边，避免内部空隙再次被描边填满。
3. 字形多于 255 个后，旧的 8 位缓存编号会重复，可能显示错字。描边字库改用稀疏码点表和较宽的缓存键。
4. 英文按空格折行，中文常无空格，因此正文排版器增加中文标点禁则。源代码里相邻的引号会被 C 编译器拼成一个字符串；只有字符串内部的反斜杠 n 才是画面换行。中文和英文宽度不同，句中换行无需逐字相同，但必须适配文本框。
5. 译文导入器现在仅导入阶段 5，保留草稿供审校。咖啡馆原版用于垂直排版的首尾空行已恢复；七条较长译文重新断行，关卡说明的多余空行也已去掉。注释说明了文件级改动，未校对的源码条目带 TODO 未校对。

## 给第一次看字库代码的说明

- 当前确实是原生字模和外部生成中文字模混用。原版英文、数字、假名、按钮图标和许多标点继续使用原生字模；中文主要从固定版本的 Fusion Pixel 生成，缺字回退到 GNU Unifont。“蹑”的小号正文和标题另有手工 9×9 骨架，标题再添加较薄的描边。外部字体只在制作 ROM 时下载和转换，游戏运行时不联网。
- “生成标题 CJK 描边字体并扩展稀疏字形缓存”其实合并说了两项改动：一项负责制作标题中文字模，另一项负责修正游戏内部的字模复用编号；“稀疏缓存”不是一种新字体。
- 标题中文字模把开源字体的汉字骨架做成 16×16、4bpp 的字身、描边和阴影，尽量接近原版标题风格。原游戏没有可直接复用的完整简体中文字库，所以生成中文后与原生英文存在少量风格差异。
- 标题字库只收录译文实际用到的汉字，就像旅行只带会穿的衣服，不把整个衣柜搬进 ROM。Unicode 查找表记录“这个汉字的字模放在第几个位置”，不用为整个 U+4E00–U+9FFF 范围预留大量空槽。
- “字形缓存”是游戏把当前要显示的字模复制到 GBA 图块显存并记录其编号，之后遇到同一个字可以复用；它不是网络缓存。旧编号只有 8 位，超过 255 个字后可能撞号，现改为同时包含字号、字库区段和字形序号的较宽键。

## 给第一次看 C 代码的排版说明

- 说唱脚本里的 .b:1、.b:0 一类标记不是台词，而是改变后续字的颜色或状态。中文词序变化时可以移动两段文字的分界，但不能删掉或调换这三组标记；具体在哪个字变色，仍要看游戏画面。
- 连着写的 `"第一段" "第二段"` 在编译时会成为同一个字符串；源码换行本身不会让游戏文字换行。字符串内部的 `\n` 才会在画面上另起一行。因此中文源码的分段不需要和英文源码逐行相同。
- 咖啡馆打印器的 `text_printer_create_new(..., 6, 176, 32)` 中，`6` 是最多六行，`176` 是每行 176 像素；不能把 `32` 当作文本框高度。跳关提问目前是四行（正文两行、选项两行），完美挑战提问是三行（正文一行、选项两行）。
- `\0051`、`\0015` 等字节用于强调文字；`\001l` 会改用大号字。只翻译它们之间能看到的英文，保留原有控制码顺序和两个菜单选项对应的“是/否”分支，避免文字正确但高亮、字号或选项逻辑损坏。
- 静态字宽估算：跳关提问最长正文 143/176 像素，最宽选项 101/176；完美挑战提问 115/176；“所有的额外关卡”大号字 169/176，只有约 7 像素余量。以上是字模宽度静态计算，不代替模拟器查看自动折行、光标和长关卡名。
