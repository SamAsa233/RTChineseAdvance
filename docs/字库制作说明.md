# 中文字库是怎样制作并放进 ROM 的

更新时间：2026-09-29  
适用分支：`font/text-localization`

这份文档面向第一次接触本项目字库代码的人。重点说明字体从哪里来、脚本怎样把字体变成点阵、点阵怎样链接进 ROM，以及游戏运行时怎样找到并显示一个汉字。

## 先说结论

如果以前做嵌入式时用过下面这种字库：

```c
const unsigned char font_zhong[] = {
    0x00, 0x10, 0x7C, 0x10,
    /* …… */
};
```

本项目的原理是一样的：**每个字最终仍是一串点阵字节，并且会被链接进 ROM。**

区别只是这里不手工维护几万个十六进制数字。制作流程是：

```text
开源字体文件
    ↓ Python 读取字形
黑白或四级颜色点阵
    ↓ 按 GBA 使用的顺序打包
.bin / .raw.4bpp 文件
    ↓ Makefile 调用 bin2s
目标文件和链接符号
    ↓ 链接器
GBA ROM
```

所以它仍然是“生成数组再放进去”，只是把手工抄数组改成了可重复运行的生成工具。

## 一、为什么看起来混用了原生字体

当前 ROM 有意保留了原游戏的一部分字模：

- 英文字母、数字、假名、按钮图标和许多标点继续使用原生字模。
- 简体中文汉字由本项目生成并补进原字库范围。
- 标题使用另一套带描边和阴影的 16×16 字模。
- “蹑”等少数生成效果不好的复杂字使用手工点阵。

这样做的原因是原版字体已经和按钮、菜单宽度、数字排列及旧文本布局配套。如果把所有英文和数字也换成外部字体，会让大量原有界面的字宽和风格一起变化。

因此这不是程序随机选择了两种字体，而是按 Unicode 范围明确分工：原生字库负责已有字符，新增字库负责中文汉字。

正文的范围表位于：

```text
data/text_printer_data.c
```

例如小号字体依次登记 ASCII、拉丁字符、标点、假名、CJK 汉字和按钮图标等范围。遇到汉字时才会进入新增的 U+4E00–U+9FFF 字库。

## 二、字体文件从哪里来

下载脚本是：

```text
tools/font/fetch_fonts.py
```

当前固定使用：

- Fusion Pixel v2026.09.01
  - 10px 简体中文比例字体
  - 12px 简体中文比例字体
- GNU Unifont 17.0.05

脚本不是每次随便下载“最新版”，而是同时固定：

1. 下载地址；
2. 版本号；
3. SHA-256 校验值；
4. 对应的许可证文本。

这样不同电脑在同一份代码上生成的字模不会因为上游字体更新而突然变化。

下载和解压后的文件放在：

```text
tools/font/third_party/
```

这个目录主要是构建输入。游戏运行时不会联网，也不会读取电脑里安装的字体。真正进入 ROM 的是生成后的点阵字节。

## 三、先确定需要哪些汉字

文本流水线会读取译文归档并生成字符集合：

```powershell
python tools/text/pipeline.py extract
```

主要输出：

```text
build/text_report/charset.txt
```

正文字库会包含：

- GB2312 能表示的常用汉字；
- 译文中实际出现的额外汉字；
- 项目明确补充的标点，例如 U+2014 破折号。

先提取字符集合有两个好处：

- 新译文增加汉字时，重新生成字库即可补字；
- 检查工具可以在构建前报告缺字，不必进游戏后才发现方框。

## 四、正文小号、中号和大号字库

生成脚本是：

```text
tools/font/build_text_font.py
```

运行命令：

```powershell
python tools/font/build_text_font.py --size all --charset build/text_report/charset.txt
```

### 4.1 字形来源顺序

脚本会根据字号选择合适的来源：

- 小号：优先使用 Fusion Pixel 10px；缺字时尝试 Fusion Pixel 12px 点采样，再回退到 Unifont。
- 中号：优先使用 Fusion Pixel 12px；缺字时回退到 Unifont。
- 大号：优先从 Unifont 生成 15px 骨架；缺字时再使用 Fusion Pixel。
- 特殊手工字：直接使用代码中定义的点阵骨架。

“回退”表示第一个字体没有这个字符时，再去第二个字体找，并不是把两个字体叠在一起。

### 4.2 为什么不能简单缩放

点阵字体没有无限分辨率。把 16×16 的复杂汉字压到 9×9 时，如果把一个区域内的像素全部做 OR 合并，原本分开的笔画可能粘在一起。

当前小号和中号回退字形采用点采样：每个目标像素从源图中央选择一个像素，减少粗暴合并造成的实心块。

“蹑”仍然过于复杂，因此在 `SMALL_MANUAL` 中有一份手工 9×9 骨架：

```text
###.#####
#.#..#.#.
###..###.
.#...#.#.
##...###.
#.#..#.#.
.##..###.
..#.#.#.#
##..#.#.#
```

其中 `#` 表示点亮，`.` 表示留空。中间保留的空列用于区分“足”和“聂”两个部件。

### 4.3 正文字模怎样打包

正文使用 1bpp 点阵，也就是每个像素只有两种状态：

- 0：透明或背景；
- 1：文字像素。

每行按 16 个像素保存，因此一行是 2 字节：

| 字号 | 保存高度 | 每个字占用 |
|---|---:|---:|
| 小号 | 12 行 | 24 字节 |
| 中号 | 12 行 | 24 字节 |
| 大号 | 16 行 | 32 字节 |

另外还有一份宽度表，每个字符用 1 字节记录实际显示宽度。文字排版器通过宽度表决定下一个字从哪里开始。

### 4.4 为什么正文文件看起来很大

正文按连续 Unicode 范围保存：

```text
U+4E00 ～ U+9FFF
```

一共有 20,992 个槽位。查找方式很像嵌入式里的固定索引数组：

```c
index = codepoint - 0x4E00;
glyph = glyph_data + index * bytes_per_glyph;
```

没有使用的槽位会保持为零。这样文件较大，但运行时查找简单、快速。

生成文件位于：

```text
bin/font/small/small_cjk_unified_ideographs_4E00_9FFF.bin
bin/font/medium/medium_cjk_unified_ideographs_4E00_9FFF.bin
bin/font/large/large_cjk_unified_ideographs_4E00_9FFF.bin
```

对应的字宽文件名称中会带有 `spacing`。

按当前格式计算：

- 小号字模文件：20,992 × 24 = 503,808 字节；
- 中号字模文件：20,992 × 24 = 503,808 字节；
- 大号字模文件：20,992 × 32 = 671,744 字节；
- 每份字宽表：20,992 字节。

## 五、标题描边字库

标题生成脚本是：

```text
tools/font/build_outline_font.py
```

运行命令：

```powershell
python tools/font/build_outline_font.py
```

### 5.1 标题不是正文加粗

标题使用 16×16、4bpp 纹理。4bpp 表示一个像素占 4 位，可以使用 16 个颜色编号。当前生成器主要使用这些层次：

- 8：深色描边；
- 9：下方阴影；
- 10：靠近底部的较暗字身；
- 11：较亮字身。

每个标题字占用：

```text
16 × 16 × 4 bit = 1024 bit = 128 字节
```

生成器先取得黑白汉字骨架，再向四周扩展描边，最后补下方阴影。这就是“生成标题 CJK 描边字体”的含义。

### 5.2 为什么标题采用稀疏字库

如果标题也为 U+4E00–U+9FFF 的 20,992 个字符全部预留 128 字节，需要约 2.56 MiB，还不包括宽度和索引。这会直接浪费 GBA ROM 空间，也没有必要为不会出现的标题字准备纹理。

标题只保存译文中实际出现的汉字，例如：

```text
节、奏、天、国……
```

生成器同时写出一个排序后的 Unicode 码点表：

```c
const u16 bitmap_font_warioware_outline_cjk_codepoints[] = {
    0x4E00, 0x4E07, /* …… */
};
```

运行时通过二分查找找到汉字在纹理文件里的序号。因此标题字库被称为“稀疏字库”：Unicode 编号可以相隔很远，文件里只连续存放真正使用的字形。

码点表和宽度表写入：

```text
data/font_definitions.c
```

标题纹理写入：

```text
graphics/font/outline/small/bitmap_font_warioware_outline_small_cjk_used.raw.4bpp
graphics/font/outline/large/bitmap_font_warioware_outline_large_cjk_used.raw.4bpp
```

### 5.3 “蹑”的标题为什么单独处理

标题原先使用八方向描边，也就是上下左右和四个对角线都扩展一圈。普通汉字效果较好，但“蹑”的 9×9 骨架非常密，八方向扩展会填满内部空隙。

当前处理是：

1. 小号标题复用正文的手工 9×9 “蹑”骨架；
2. 只向上、下、左、右四个方向描边；
3. 其他标题字继续使用原来的完整描边。

这就是为什么修改“蹑”时，正文和标题需要分别检查。它们走的是两套字库和两条渲染路径。

## 六、`.bin` 怎样变成 ROM 里的数组

Makefile 会收集 `bin/` 目录下的 `.bin` 和标题目录下的 `.raw.4bpp` 文件，然后调用：

```text
bin2s
```

对应规则在 `Makefile` 中：

```make
$(BUILD)/%.bin.o $(BUILD)/%.bin.h : %.bin
	bin2s ... | arm-none-eabi-as ...
```

`bin2s` 会把二进制文件转换成汇编数据和符号，再由汇编器生成 `.o` 目标文件。链接器把目标文件放进 ROM，并生成类似下面的可引用符号：

```c
small_cjk_unified_ideographs_4E00_9FFF_bin
small_spacing_cjk_unified_ideographs_4E00_9FFF_bin
```

从 C 代码角度看，这些符号就像：

```c
extern const unsigned char small_cjk_unified_ideographs_4E00_9FFF_bin[];
```

因此它和手写 `const unsigned char font[]` 的最终结果相同，只是字节来自自动生成的二进制文件。

## 七、游戏运行时怎样找到一个字

### 7.1 正文字库

正文范围表在：

```text
data/text_printer_data.c
```

文字打印器解码 UTF-8 后得到 Unicode 码点，例如“中”是 U+4E2D。它在范围表中找到 U+4E00–U+9FFF，然后用：

```text
U+4E2D - U+4E00
```

得到字模槽位，再从 1bpp 字模和字宽表中读取数据。

### 7.2 标题字库

标题运行时代码在：

```text
src/bitmap_font.c
```

处理步骤是：

1. `utf8_decode_codepoint()` 把 UTF-8 字节解码成 Unicode 码点；
2. `bmp_font_codepoint_to_glyph()` 找到对应字库范围；
3. 如果范围有 `codepointList`，就在稀疏码点表中二分查找；
4. 得到纹理序号和字宽；
5. 把 16×16 字模复制到 GBA 的 OBJ 显存；
6. 创建文字精灵并显示。

### 7.3 字形缓存是什么

把每个字重复复制到显存很浪费，所以运行时会记录已经上传过的字形。下一次再显示同一个字时，可以直接复用原来的图块。

缓存键现在包含：

```text
字号 + 字库区段 + 字形序号
```

旧实现只使用较短的字形序号。中文字超过 255 个后，不同字可能出现相同编号，导致缓存误以为“这个字已经上传”，最后显示成另一个字。

“扩展稀疏字形缓存”并不是制作了一种新字体，而是修正运行时记录字形身份的方式。

## 八、完整生成步骤

在项目根目录依次运行：

```powershell
# 1. 下载固定版本字体并校验哈希和许可证
python tools/font/fetch_fonts.py

# 2. 从译文中提取需要的字符
python tools/text/pipeline.py extract

# 3. 生成正文小、中、大三档字库
python tools/font/build_text_font.py --size all --charset build/text_report/charset.txt

# 4. 生成标题描边字库和稀疏码点表
python tools/font/build_outline_font.py

# 5. 检查字模编码能否正确往返
python tools/font/test_tengoku_font.py

# 6. 检查译文是否缺字、控制码是否一致
python tools/text/check_text.py
```

最后按项目正常流程编译 ROM。Makefile 会自动把生成的 `.bin` 和 `.raw.4bpp` 文件链接进去。

## 九、新增译文后怎样补字

如果只是译文中出现了新汉字，通常不需要手工改 C 数组：

1. 更新译文；
2. 运行 `pipeline.py extract`；
3. 重新运行正文和标题字库生成脚本；
4. 运行字库与文本检查；
5. 编译 ROM 并查看实际画面。

如果检查显示缺字，先确认固定版本的 Fusion Pixel 或 Unifont 是否包含该字符。两个字体都没有，或者缩小后效果很差时，再增加手工骨架。

## 十、怎样手工修一个生成不好的字

以小号“蹑”为例，入口在：

```text
tools/font/build_text_font.py
```

字形保存在 `SMALL_MANUAL` 字典中。修改时应注意：

- 行数必须符合目标高度；
- 每行宽度必须一致；
- `#` 是点亮像素，`.` 是空像素；
- 左右部件之间要保留必要空隙；
- 修改正文后还要检查标题是否复用了该骨架；
- 生成后必须运行回归检查并进入实际场景查看。

标题还支持通过 PNG 预览和 `outline_manual.txt` 选择人工修图，但 Pillow 只用于预览和人工入口，正常 ROM 构建不依赖 PNG。

## 十一、常见误区

### “是不是把网上的字体直接塞进游戏？”

不是。脚本从固定版本的开源字体中读取单个字形，再转换成游戏能使用的点阵格式。TTF/BDF/HEX 原文件不会在游戏运行时被解析。

### “为什么不把整个字体文件放进 ROM？”

GBA 没有操作系统字体渲染器，也不适合运行时解析现代字体。提前生成点阵更简单、更快，也更容易控制 ROM 大小。

### “是不是每个汉字都对应一个数组？”

逻辑上是。正文把许多定长字形连续放进一个大二进制数组，标题把实际使用的字形连续存放，并用码点表指出每个字的位置。

### “为什么正文连续保存，标题却稀疏保存？”

正文每字只有 24 或 32 字节，连续范围查找简单；标题每字 128 字节，如果给两万多个汉字全部留槽会浪费约 2.56 MiB，所以只保存实际用字。

### “字宽和字模是一回事吗？”

不是。字模决定哪些像素点亮，字宽决定下一个字符从哪里开始。字模正常但宽度错误时，仍可能出现字符重叠或间距过大。

### “为什么生成成功还要实机检查？”

自动检查能发现缺字、文件尺寸、像素数量和控制码错误，但不能完全判断一个复杂汉字是否清楚，也不能代替游戏中的文本框、描边、颜色和背景效果。

## 十三、用嵌入式开发的说法总结

可以把整套方案理解为：

1. Python 是“上位机字模生成工具”；
2. `.bin` 是生成好的点阵数组原始数据；
3. `bin2s` 相当于自动生成 `const unsigned char[]`；
4. Unicode 范围表或稀疏码点表相当于字符到数组偏移的索引；
5. ROM 是 Flash；
6. GBA VRAM 是显示时使用的显存缓冲区；
7. 字形缓存记录哪些点阵已经复制进 VRAM。

所以这套实现与你以前逐字生成数组的思路没有本质区别，只是把字符收集、字体取样、数组生成、索引生成和检查自动化了。
